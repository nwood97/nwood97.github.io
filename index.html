Featured: automated carrier compliance

SuiteScript 2.1 · REST API · Scheduled + User Event · shared library

Trucking vendors have to hold valid federal operating authority and meet the company's own insurance and paperwork rules. Checking each carrier by hand against the FMCSA SAFER data was slow and easy to let lapse, so I built a compliance engine inside NetSuite that checks carriers automatically, on a schedule and the moment a vendor is saved.

What I built

  • An integration with an FMCSA/SAFER data provider that picks the right endpoint from the carrier's USDOT or MC number and parses the JSON response.
  • One shared compliance library holding the API calls, normalisation, business rules, record updates and logging.
  • A Scheduled Script that re-checks eligible carriers from configurable saved searches, with run limits for controlled tests.
  • A User Event (afterSubmit) that checks a trucking vendor on create or edit, gated by form and vendor category.

Rules it enforces

  • Federal operating authority and status from FMCSA.
  • Auto, cargo and general liability coverage, with currency values normalised before comparison.
  • Insurance expiry against a configurable warning window.
  • Signed carrier agreement and insurance certificate on file, plus internal authorisation flags.
  • Fleet size (power units) pulled to the vendor, with zero kept distinct from missing.

Engineering details

  • Never overwrites good stored data when the external service fails or returns blanks.
  • Every failed rule becomes a plain-English reason on the vendor record.
  • Duplicate vendors across searches are de-duplicated with a Set and responses are cached per run.
  • Obviously invalid carrier numbers are rejected before any request is made.
  • A diagnostic mode proved eligibility logic in Production before updates were switched on.

Result

Tested against live Production vendor records; the vendor-save check is confirmed working. Compliance status, the reasons behind it and the last check date now sit on the vendor record itself, ready for saved-search reporting, and any rule change is made once in the shared library.

Sample code

A pattern I use often: one Client Script deployed to several custom record types, driven by a per-record field map, so the rule lives in one file. Here, choosing Bulk packaging clears and locks the packaging quantity; a matching User Event clears it again on save in case the browser script didn't run.

Field and list IDs are changed from the real account.

bulk-packaging-client.js
/**
 * @NApiVersion 2.1
 * @NScriptType ClientScript
 */
define([], () => {
  const BULK_ID = '3';
  // One map per record type: one script, many deployments
  const CONFIG = {
    customrecord_sales_contract:    { packaging: 'custrecord_sc_pack_type', qty: 'custrecord_sc_pack_qty' },
    customrecord_purchase_contract: { packaging: 'custrecord_pc_pack_type', qty: 'custrecord_pc_pack_qty' },
    customrecord_phase:             { packaging: 'custrecord_ph_pack_type', qty: 'custrecord_ph_pack_qty' }
  };

  const getConfig = (rec) => CONFIG[rec.type] || null;

  function updatePackagingQty(rec) {
    const cfg = getConfig(rec);
    if (!cfg) return;
    const isBulk = String(rec.getValue({ fieldId: cfg.packaging }) || '') === BULK_ID;
    const field = rec.getField({ fieldId: cfg.qty });

    if (isBulk) {
      if (field) field.isDisabled = false;   // unlock so the value can be cleared
      rec.setValue({ fieldId: cfg.qty, value: null, ignoreFieldChange: true });
    }
    if (field) field.isDisabled = isBulk;
  }

  function pageInit(ctx) { updatePackagingQty(ctx.currentRecord); }

  function fieldChanged(ctx) {
    const cfg = getConfig(ctx.currentRecord);
    if (cfg && ctx.fieldId === cfg.packaging) updatePackagingQty(ctx.currentRecord);
  }

  return { pageInit, fieldChanged };
});
